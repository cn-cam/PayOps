# 部署手册

同一份代码支持三种部署形态，区别只在进程数量与 `PayOps:Roles`。

| 形态 | 适用 | 进程 | 高可用 |
| --- | --- | --- | --- |
| 单体 | 开发、内部小流量 | 1 个进程，`Roles=All` | 无（可在多台机器各起一个单体进程 + 负载均衡，即成为多副本） |
| Docker Compose | 单机多副本、预发 | `api`×N + `worker`×N + Nginx | 进程级 |
| Kubernetes | 生产 | `gateway`×3 + `admin`×2 + `worker`×2，HPA 自动扩缩 | 节点 / 可用区级 |

## 1. 配置项

所有配置都在 `PayOps` 节，可用 `appsettings.{Environment}.json` 或环境变量（层级用 `__`，如 `PayOps__Database__ConnectionString`）。

| 配置 | 说明 |
| --- | --- |
| `PayOps:Roles` | `All` 或 `Gateway` / `Admin` / `Worker` 的逗号组合 |
| `PayOps:PublicBaseUrl` | 对外地址，用于拼上游回调地址 `{PublicBaseUrl}/api/notify/{provider}/{passageId}`。生产必须是公网 HTTPS |
| `PayOps:Database:ConnectionString` | MySQL 连接串（必须带 `Database=`）。首次启动自动建库建表 |
| `PayOps:Database:AutoMigrate` | 默认 `true`。想由 DBA 手工执行脚本时设为 `false` |
| `PayOps:Redis:ConnectionString` | StackExchange.Redis 格式，支持 Sentinel（`serviceName=`）与 Cluster |
| `PayOps:RabbitMq:Hosts` | `host:port`，集群填多个（逗号分隔） |
| `PayOps:RabbitMq:QueueType` | `quorum`（默认，集群下多副本持久）或 `classic`。**队列创建后不可更改类型** |
| `PayOps:Security:MasterKey` | 凭证落库加密主密钥。**所有副本一致；丢失后已保存凭证无法解密，必须备份** |
| `PayOps:Security:JwtKey` | 后台令牌签名密钥，所有副本一致 |
| `PayOps:Security:InitAdminPassword` | 首次启动创建 `admin` 账号的初始密码 |
| `PayOps:TimeZoneOffsetHours` | 业务时区，默认 8（影响日限额、时段、报表按天） |
| `PayOps:EnableDemoEndpoints` | 演示接收端，生产保持 `false` |

健康检查：`/healthz/live`（存活）、`/healthz/ready`（就绪，数据库可用才返回 200）。

## 2. 本地开发

需要本机可访问的 MySQL（3306）、Redis（6379）、RabbitMQ（5672）。把 `src/PayOps.Server/appsettings.Local.example.json` 复制为 `appsettings.Local.json` 并填写真实账号——该文件被 `.gitignore` 忽略，优先级高于其他配置文件，凭证不会进入代码库。

```powershell
# 后端（http://localhost:5080，自动建库 payops）
dotnet run --project src/PayOps.Server

# 管理后台（http://localhost:5175，/api 代理到 5080）
cd web/admin; npm install; npm run dev

# 端到端演示 / 冒烟测试
pwsh scripts/demo.ps1
```

默认账号 `admin` / `Admin@123456`。

## 3. 单体部署

```powershell
pwsh deploy/standalone/publish.ps1                      # 产物在 artifacts/payops
pwsh deploy/standalone/publish.ps1 -Runtime linux-x64   # 自包含（目标机免装运行时）
```

Linux 可用 `deploy/standalone/publish.sh`。然后：

1. 把 `appsettings.Production.example.json` 复制为 `appsettings.Production.json` 并填写；
2. 启动：`ASPNETCORE_ENVIRONMENT=Production dotnet PayOps.Server.dll`（Windows：`$env:ASPNETCORE_ENVIRONMENT="Production"; dotnet PayOps.Server.dll`）；
3. Linux 常驻参考 `deploy/standalone/payops.service`（systemd）；
4. 前面放 Nginx/Caddy 做 HTTPS，并把 `/api/admin` 与 `/` 限制为内网访问。

管理后台静态资源在产物的 `wwwroot` 下，由同一进程托管。

> 单体不是"另一套代码"：在第二台机器再起一个同样的进程、指向同一组中间件，就是两副本。

## 4. Docker Compose

镜像（同一个镜像承担所有角色）：

```bash
docker build -f deploy/docker/Dockerfile -t payops:1.1.0 .
# 国内可加：--build-arg NPM_REGISTRY=https://registry.npmmirror.com
```

### 4.1 完整栈（自带中间件）

```bash
cd deploy/compose
cp .env.example .env          # 修改所有口令与密钥
docker compose up -d --build
# 管理后台 http://localhost:8090
docker compose up -d --scale api=4 --scale worker=3     # 扩容
```

### 4.2 复用本机演示中间件（多副本演示）

```bash
cd deploy/compose
cp .env.dev.example .env.dev  # 填写 mysql.dev / rabbitmq.dev 的账号
docker compose -f docker-compose.dev.yml --env-file .env.dev up -d --build
pwsh ../../scripts/demo.ps1 -BaseUrl http://localhost:8090 -InternalBaseUrl http://nginx
```

后台"仪表盘 → 集群节点"能看到 2 个 `Gateway,Admin` 与 2 个 `Worker` 副本及各自的节点号。

验证高可用：`docker kill` 任意一个 api 或 worker 容器，下单与通知不受影响（Nginx 自动重试下一个副本；未确认的消息由另一个 worker 接手）。

## 5. Kubernetes

清单为 Kustomize：`deploy/k8s/base` + `overlays/demo`（自带单实例中间件）/ `overlays/prod`（外部中间件）。

```bash
# 演示
kubectl apply -k deploy/k8s/overlays/demo
kubectl -n payops get pods
kubectl -n payops port-forward svc/payops-admin 8090:80

# 生产
cd deploy/k8s/overlays/prod
cp secret.env.example secret.env        # 填写真实连接信息（不要提交）
# 修改 kustomization.yaml 中的镜像地址、域名、TLS Secret
kubectl apply -k .
```

| 资源 | 说明 |
| --- | --- |
| `Deployment payops-gateway`（3 副本，HPA 3~12） | 公网入口 `/api/pay`、`/api/notify` |
| `Deployment payops-admin`（2 副本） | 管理后台，独立 Ingress，建议内网 + 白名单 |
| `Deployment payops-worker`（2 副本，HPA 2~8） | 后台任务，无需选主 |
| `PodDisruptionBudget` ×3 | 节点维护时保留最小可用副本 |
| `topologySpreadConstraints` | 副本打散到不同节点 / 可用区 |
| 探针 | `startupProbe` + `readinessProbe(/healthz/ready)` + `livenessProbe(/healthz/live)` |
| `preStop sleep 8` + `terminationGracePeriodSeconds 45` | 先摘流再停机，滚动发布不丢请求 |
| `securityContext` | 非 root、只读根文件系统、去除全部 capabilities |

发布新版本：改 `images.newTag` 后 `kubectl apply -k`；`maxUnavailable: 0` 保证滚动期间容量不降。数据库迁移在新副本启动时自动执行（`GET_LOCK` 互斥），**结构变更需保持向后兼容**（先加列、后用、再删旧）。

## 6. 中间件高可用建议

| 中间件 | 建议 |
| --- | --- |
| MySQL | MGR / 主从 + 自动切换（或云 RDS 高可用版），应用连接写 VIP；开启 binlog 与定期备份 |
| Redis | Sentinel 或 Cluster。Redis 短暂不可用时 PayOps 会降级放行，不影响主链路 |
| RabbitMQ | 3 节点集群 + 仲裁队列（默认 `QueueType=quorum`）。不可用期间任务留在数据库，恢复后自动补发 |

## 7. 上线检查清单

- [ ] `MasterKey`、`JwtKey` 为强随机值且已备份；`admin` 初始密码已修改
- [ ] `PublicBaseUrl` 为公网 HTTPS 域名，且各通道的回调地址已按 `06-通道接入指南.md` 配置到对应平台
- [ ] `/api/admin` 与管理后台仅内网可达
- [ ] `EnableDemoEndpoints=false`，正式渠道未绑定模拟通道
- [ ] 每个真实通道至少完成一笔"下单 → 支付 → 回调 → 业务通知 → 退款"的真实联调
- [ ] 监控：就绪探针、后台仪表盘的"待通知 / 通知失败 / 处理中退款"、RabbitMQ 队列堆积、日志中的 `金额不一致` / `上游交易号已被其他订单使用` / `熔断`
