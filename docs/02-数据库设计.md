# 数据库设计

- MySQL 8.0，`utf8mb4`。结构脚本：`src/PayOps.Service/Data/Migrations/V001__init.sql`（内嵌进程序集，启动时自动执行）。
- **所有时间列为 UTC**（`DATETIME(3)`），金额单位为**分**（`BIGINT`）。
- 新增结构变更：新建 `V002__xxx.sql`，已执行版本记录在 `schema_version`，多副本启动由 `GET_LOCK` 互斥。

## 1. 关系

```text
pay_app 1 ── N pay_channel 1 ── N pay_channel_passage N ── 1 pay_passage
   │                                                          │
   └── N pay_order ── N pay_refund                            │
            │  passage_id / binding_id ───────────────────────┘
            └── pay_notify_task（type=1 订单号 / type=2 退款单号）
pay_upstream_notify（上游回调原始日志）   sys_user / sys_audit_log（后台）
```

## 2. 配置表

| 表 | 说明 | 关键约束 |
| --- | --- | --- |
| `pay_app` | 应用。`secret_cipher` 为接入密钥密文 | `uk(app_code)` |
| `pay_channel` | 渠道，隶属应用 | `uk(app_id, code)` |
| `pay_passage` | 通道。`provider` 支付类型，`config_cipher` 凭证 JSON 密文 | `idx(provider)` |
| `pay_channel_passage` | 渠道通道绑定（路由规则）：`methods / weight / priority / min_amount / max_amount / daily_limit_amount / daily_limit_count / start_time / end_time / status` | `idx(channel_id)`、`idx(passage_id)`；同一通道允许在同一渠道绑定多条（用于金额分档） |

## 3. 交易表

### pay_order

| 列 | 说明 |
| --- | --- |
| `order_no` | 平台订单号（21 位：前缀 + 时间 + 节点号 + 序列），同时作为上游商户订单号 |
| `app_id` / `mch_order_no` | 业务订单号，应用内唯一 |
| `channel_id` / `passage_id` / `binding_id` | 下单渠道、路由到的通道与命中的绑定 |
| `provider` / `pay_method` | 支付类型 / 方式 |
| `amount` / `refund_amount` | 订单金额 / 已占用退款额（处理中 + 成功） |
| `status` | 0 待支付，1 成功，2 关闭，3 失败（所有通道下单失败） |
| `upstream_trade_no` | 上游交易号 |
| `credential` | 下单返回给客户端的支付凭据（用于幂等重入） |
| `expire_at` / `next_check_at` / `check_count` | 过期时间；下次巡检时间（兼作派发租约）；已巡检次数 |

| 索引 | 用途 |
| --- | --- |
| `uk_order_no` | 主查询键 |
| `uk_app_mch_order (app_id, mch_order_no)` | 下单幂等 |
| `uk_upstream (provider, upstream_trade_no)` | **同一上游交易只能入账一笔订单**（防凭证重放）；NULL 不参与唯一 |
| `idx_check (status, next_check_at)` | 巡检派发 `FOR UPDATE SKIP LOCKED` |
| `idx_created`、`idx_channel_created`、`idx_passage_created`、`idx_user` | 后台查询与统计 |

状态机（全部通过条件更新实现，天然幂等）：

```text
待支付(0) ──支付成功──> 成功(1)
待支付(0) ──超时/主动关闭──> 关闭(2) ──迟到的支付成功──> 成功(1)
待支付(0) ──所有通道下单失败──> 失败(3) ──相同 mchOrderNo 重新下单──> 待支付(0)（换新 order_no）
```

### pay_refund

`uk(refund_no)`、`uk(app_id, mch_refund_no)`（幂等）。`status`：0 处理中，1 成功，2 失败。`source`：`api` / `admin` / `upstream`（商店侧发起的退款，本地补建）。可退余额在 `pay_order.refund_amount` 上原子占用，失败时释放。

### pay_notify_task（事务发件箱）

`uk(type, biz_no)` 保证每笔订单/退款只有一个通知任务。`next_time` 既是下次投递时间，也是派发租约；`event_published` 标记领域事件是否已发到 MQ。`status`：0 待通知，1 成功，2 失败（重试耗尽，可后台重发）。

### pay_upstream_notify

上游回调原始日志（验签结果、处理结果、截断的请求体），用于排障与审计。

## 4. 容量与运维建议

- 订单量大时按月归档 `pay_order / pay_refund / pay_notify_task / pay_upstream_notify`（历史数据迁到归档库），或对 `pay_order` 按 `created_at` 做 RANGE 分区（注意分区表的唯一键必须包含分区列，需相应调整）。
- 生产 MySQL 建议 MGR 或主从 + 自动切换；应用只连写入口。
- 连接串可加 `MaximumPoolSize=100` 等参数；每个副本一个连接池。
