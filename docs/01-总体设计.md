# PayOps 总体设计

PayOps 是一套**自用**的分布式高可用支付系统：公司自己的多个产品（应用），通过各自的分发渠道，使用公司自己名下的多套支付凭证收款。

## 1. 需求理解：自用 · 多渠道 · 多通道

### 1.1 "自用"意味着什么

| 聚合支付平台（不是本系统） | 自用支付系统（本系统） |
| --- | --- |
| 面向外部商户，有进件、代理、费率、分账、结算、提现 | 没有商户体系：收款主体就是公司自己，钱直接进公司自己的商户号/商店账号 |
| 通道是"上游服务商"，按费率成本路由 | 通道是**自己名下的一套凭证**（商户号、应用密钥），按可用性、限额、风控分散路由 |
| 接入方不可信，需要强隔离 | 接入方是自己的业务服务端，用应用密钥做 HMAC 签名即可 |

所以本系统只有四个核心配置对象，没有商户/代理/费率/结算模块：

```text
应用 App ──1:N──> 渠道 Channel ──N:M（绑定=路由规则）──> 通道 Passage ──N:1──> 支付类型 Provider
（自有产品）       （分发渠道）                           （一套凭证）            （微信/支付宝/…）
```

### 1.2 渠道（Channel）

渠道是**应用的分发渠道**：同一个产品会打出"官方包、华为包、OPPO 包、vivo 包、小米包、荣耀包、App Store 包"，还可能有"微信小程序、抖音小程序、H5 官网"。不同渠道**能用什么支付是被渠道规则决定的**：

| 渠道示例 | 可用的支付类型 | 原因 |
| --- | --- | --- |
| 官方包 / 官网 H5 | 微信支付、支付宝 | 自有分发，直连支付 |
| 微信小程序 | 微信支付（JSAPI） | 平台限制 |
| 抖音小程序 | 抖音支付 | 平台限制 |
| 华为 / 荣耀 / OPPO / vivo / 小米 应用商店包 | 对应商店的应用内支付 | 联运协议要求走商店支付 |
| App Store 包 | 苹果应用内购买 | 审核规则要求走 IAP |

因此"**按渠道配置支付通道**"是这套系统的第一原则：业务下单时只需要说"我是哪个应用的哪个渠道、用户选了哪种支付方式、多少钱"，其余由系统决定。

### 1.3 通道（Passage）与"一个渠道多个通道"

通道 = 某个支付类型下的**一套凭证**，例如"微信支付-主体甲-商户号 1900000001""微信支付-主体乙-商户号 1900000002""华为 IAP-游戏 X"。通道全局维护，可被多个渠道复用。

一个渠道可以绑定多个通道，**同一支付类型也可以绑定多个**，典型原因：

- **风控分散 / 限额**：单个商户号有单笔、单日限额或风控阈值，把流量按权重摊到多个商户号；
- **容灾**：某个商户号被限制、证书过期、上游抖动时，自动切到其他商户号；
- **灰度**：新商户号先给 5% 权重观察；
- **按金额分流**：小额走 A，大额走 B（起付金额 / 单笔上限）；
- **按时段**：某些通道只在特定时段使用。

这些规则配置在"渠道 ↔ 通道"的**绑定**上，而不是通道本身——同一个通道在不同渠道里可以有不同的权重和金额区间。

### 1.4 路由规则（绑定上的字段）

| 字段 | 含义 |
| --- | --- |
| `methods` | 允许的支付方式（如只开 `wechat_app`）；空 = 该类型的全部方式 |
| `priority` | 优先级，数值小者优先；高优先级组全部不可用才使用下一组（主备） |
| `weight` | 权重，同优先级组内按权重随机分流；`0` = 备用，仅当组内没有正权重可用通道时使用 |
| `minAmount` | **起付金额**：订单金额 ≥ 该值才会选中 |
| `maxAmount` | 单笔上限，0 = 不限 |
| `dailyLimitAmount` / `dailyLimitCount` | 日成功金额 / 笔数限额（多副本共享的 Redis 计数） |
| `startTime` / `endTime` | 可用时段，支持跨零点 |
| `status` | 启停 |

### 1.5 路由算法

```text
输入：渠道、支付方式（→ 支付类型）、金额
1. 过滤：绑定启用 ∧ 通道启用 ∧ 类型匹配 ∧ 方式允许 ∧ 金额 ∈ [起付金额, 单笔上限]
        ∧ 在可用时段 ∧ 未超日限额 ∧ 未熔断
2. 排序：按 priority 分组（小者在前）；组内按 weight 做不放回加权随机；weight=0 排在组内末尾
3. 兜底：仅因"熔断中"被排除的通道追加到队尾（探测性放行，避免全部熔断时整体不可用）
4. 执行：依次尝试（默认最多 3 个）。通道下单失败 → 记失败计数 → 换下一个（故障转移）；
        60 秒内失败 5 次 → 熔断 30 秒，到期自动恢复
```

算法是 `PayOps.Core/Routing/PassageRouter.cs` 里的纯函数，真实下单与后台"路由模拟"共用同一份实现。

## 2. 系统架构

```text
                     业务服务端（HMAC 签名）          上游：微信/支付宝/抖音/各应用商店
                              │                                   │ 回调
                              ▼                                   ▼
                 ┌──────────────────────── 负载均衡 / Ingress ────────────────────────┐
                 │                                                                    │
        ┌────────▼────────┐   ┌─────────────────┐   ┌─────────────────┐   ┌──────────▼──────┐
        │ Gateway 副本 ×N │   │  Admin 副本 ×N  │   │ Worker 副本 ×N  │   │ Gateway 副本 ×N │
        │ /api/pay        │   │ /api/admin + UI │   │ 派发 + 消费     │   │ /api/notify     │
        └───┬────┬────┬───┘   └───┬────┬────────┘   └───┬────┬────┬───┘   └─────────────────┘
            │    │    │           │    │                │    │    │
            ▼    ▼    ▼           ▼    ▼                ▼    ▼    ▼
        ┌───────┐ ┌───────┐ ┌──────────┐
        │ MySQL │ │ Redis │ │ RabbitMQ │      同一个镜像/可执行文件，PayOps:Roles 决定角色
        └───────┘ └───────┘ └──────────┘
```

| 角色 | 职责 | 对外 |
| --- | --- | --- |
| `Gateway` | 业务接入 API（下单/查询/关单/退款/凭证核验）、上游回调 | 公网 |
| `Admin` | 管理后台 API + Vue3 静态资源 | 内网 |
| `Worker` | 通知派发与投递、掉单补偿、超时关单、退款巡检 | 无 |
| `All` | 以上全部（单体部署） | - |

三种角色都是**无状态**的，任何副本可随时增减或被杀掉。

### 2.1 中间件分工

| 中间件 | 用途 | 不可用时 |
| --- | --- | --- |
| **MySQL** | 唯一事实来源：订单、退款、通知任务（发件箱）、配置 | 就绪探针失败，副本被摘流；下单失败。已缓存的配置快照继续可用 |
| **Redis** | 分布式锁、nonce 防重放、通道熔断状态、日限额计数、节点号租约、节点心跳、配置变更广播 | **失败放行**：锁退化为数据库唯一键兜底，熔断/限额视为无数据，下单与回调主链路照常 |
| **RabbitMQ** | 把"通知投递""订单/退款巡检"任务分发给 Worker 副本竞争消费；对外发布领域事件 | 即时派发失败 → 任务留在数据库，恢复后由派发任务重新扫描；支付入账不受影响 |

## 3. 多副本与高可用设计

"原生支持多副本"落在下面这些具体机制上：

| 问题 | 机制 | 代码 |
| --- | --- | --- |
| 订单号多副本不冲突 | 每个副本通过 Redis 租约独占一个节点号（0~999）写入订单号；租约丢失自动重新申请；数据库唯一键兜底 | `NodeService`、`OrderNoGenerator` |
| 同一业务单并发下单 | Redis 锁 + `uk(app_id, mch_order_no)`；锁降级时以唯一键为准并返回已存在订单 | `OrderService.CreateAsync` |
| 回调重复 / 多副本同时处理同一笔成功 | 条件更新 `UPDATE … WHERE status<>1` 只会成功一次；`uk(provider, upstream_trade_no)` 防同一上游交易入账多笔订单 | `OrderService.HandlePaidAsync` |
| 状态变更与通知不一致 | 事务发件箱：订单状态与通知任务同一事务写入 | `NotifyService.InsertTaskAsync` |
| 定时任务多副本重复执行 | 不选主。派发使用 `SELECT … FOR UPDATE SKIP LOCKED` 领取 + 租约续期，各副本领到的任务互不重叠 | `NotifyService.DispatchDueAsync`、`ClaimDueChecksAsync` |
| Worker 宕机丢任务 | 消息未 ack 由 Broker 重投；任务租约到期后被重新派发；处理逻辑全部幂等 | `MqBus.ConsumeAsync` |
| 配置修改多副本生效 | 本地快照 15 秒 TTL + Redis 发布订阅即时失效 | `ConfigCache` |
| 通道故障 | 故障转移 + 多副本共享的熔断器（Redis 计数） | `RedisStore`、`PassageRouter` |
| 退款并发超退 | 单条 SQL 原子占用可退余额：`refund_amount + x <= amount` | `RefundService.CreateAsync` |
| 滚动发布不丢请求 | 就绪探针 + preStop 延时 + 30 秒优雅停机；停机时未 ack 的消息交回 Broker | `Program.cs`、`deploy/k8s` |
| 数据库迁移多副本并发启动 | MySQL `GET_LOCK` 互斥的版本化迁移 | `Migrator` |
| 密钥 | 通道凭证与应用密钥 AES-256-GCM 落库加密，主密钥由配置注入、所有副本一致 | `SecretProtector` |

## 4. 核心流程

### 4.1 直连支付（微信 / 支付宝 / 抖音）

```text
业务服务端            PayOps Gateway                上游                 PayOps Worker        业务服务端
   │ POST /api/pay/orders │                           │                        │                  │
   │─────────────────────>│ 路由 → 通道 A 下单失败 ──>│                        │                  │
   │                      │ 故障转移 → 通道 B 下单 ──>│                        │                  │
   │<──── 支付凭据 ───────│                           │                        │                  │
   │      （客户端拉起支付，用户完成付款）            │                        │                  │
   │                      │<──── 支付结果回调 ────────│                        │                  │
   │                      │ 验签 → 校验通道归属/金额  │                        │                  │
   │                      │ 事务：订单置成功 + 写通知任务                      │                  │
   │                      │──── 应答上游 success ────>│                        │                  │
   │                      │──── 任务 ID → RabbitMQ ───────────────────────────>│                  │
   │                      │                           │                        │── POST 通知 ────>│
   │                      │                           │                        │<──── success ────│
```

### 4.2 应用商店内购

| 类型 | 下单 | 支付结果确认 |
| --- | --- | --- |
| 华为 / 荣耀 | 返回 `developerPayload`（= 平台订单号），客户端传入 SDK | ① 客户端支付后把 `purchaseToken` 交给业务服务端 → `POST /api/pay/orders/verify` 回源核验；② 商店服务端通知（仅作为触发器，同样回源核验） |
| 苹果 | 返回 `appAccountToken`（订单号可逆编码的 UUID），客户端传入 `purchase(options:)` | ① 客户端提交 `transactionId` → `verify` 调 App Store Server API 取签名交易并校验证书链；② Server Notifications V2（校验 JWS 证书链到 Apple Root CA G3） |
| OPPO / vivo / 小米 | 返回 SDK 参数（vivo 含服务端签名） | 以商店服务端回调为准（RSA / MD5 / HMAC-SHA1 验签） |

内购的共同原则：**客户端上报的内容一律不直接信任**，必须回源或验签；凭证与订单通过 `developerPayload / bizOrderNo / appAccountToken` 绑定防串单；上游交易号唯一键防一证多用。

### 4.3 可靠性补偿

- **掉单补偿**：待支付订单按 30s / 60s / 120s / 300s / 600s 递进主动查询上游（支持查单的类型），查到已支付即入账；
- **超时关单**：到期先查一次上游，确认未支付再关单；关单后若仍收到支付成功，订单会被重新置为成功（宁可多通知，不丢钱）；
- **业务通知重试**：15s / 30s / 1m / 3m / 10m / 30m / 1h / 2h / 6h，共 10 次，之后可在后台手动重发；
- **退款巡检**：处理中的退款定期查询；结果未知时保持"处理中"，不自动释放可退额度。

## 5. 安全设计

- 业务接入：`HMAC-SHA256(secret, "METHOD\npath\ntimestamp\nnonce\nbody")`，±5 分钟时间窗，nonce 防重放；
- 上游回调：按各家协议验签；URL 中带通道 ID 定位密钥，验签后校验"订单确实属于该通道"；金额不一致拒绝入账；
- 凭证：落库加密；后台详情接口对密钥字段返回掩码；审计日志不记录凭证内容；
- 后台：JWT + 三级角色（admin / operator / viewer）；所有写操作记审计；
- 模拟通道与演示端点仅用于联调，生产不要绑定到正式渠道 / 不要开启。


## 7. 已知边界

- 支付宝仅实现公钥模式（未实现证书模式）；微信仅直连商户模式（未实现服务商模式）；抖音实现的是担保支付（ecpay）。
- 订阅型内购（自动续费）未实现，仅支持一次性商品。
- 日限额按"支付成功"累计，在途订单不占额度，临界时可能小幅超出。
- 未实现对账单下载与自动对账；订单表未做分库分表（建议按月归档）。
- 各真实支付类型按官方文档实现并有验签单元测试，但**尚未用真实商户凭证联调**，上线前需逐个通道验证（见 `06-通道接入指南.md`）。
